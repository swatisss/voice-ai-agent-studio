# Directory Update Log

## 2026-10-12 (CP-0013 visual evidence intake — accepted, LiveKit Cloud chosen on review)

* **Reviewed and redirected**: the first draft of CP-0013 carried camera stills on the existing call WebSocket. Review asked whether LiveKit Cloud was possible; it is, and it is now the decision. [ADR-0009](decisions/adr-0009-video-channel.md) was rewritten accordingly, [ADR-0002](decisions/adr-0002-voice-pipeline.md) gained an amendment (its "WebRTC needs UDP, which Cloud Run does not support without a TURN server" does not reach a managed SFU — LiveKit Cloud supplies TURN over TLS 443), and [media room protocol](api/media-protocol.md) is new. `channel: "voice"` keeps the WebSocket untouched, so VO-01…VO-08 are unaffected; one pipeline, two transports.
* **What the flip cost, recorded rather than buried**: Pipecat 1.12.0's LiveKit transport has no on-demand frame fetch, so a video call streams the caller's camera to a third-party SFU and into the service for as long as the camera is on. The stills option could promise nothing left the caller's machine unasked; this cannot. **Compliance rules 9 and 12 were rewritten to say so**, rule 9 names leaving LiveKit unconfigured as the out for a deployment that cannot accept third-party media transit, a BAA with the media provider joins the production gaps, and VI-03 now asserts the narrower property that holds: no frame encoded, stored or put to a model unasked, and the tap holds one frame however many arrive. VI-01, VI-02, VI-04 and VI-15 were re-expressed for rooms and the tap.
* **Verified rather than assumed, before deciding**: the transport ships in the pinned Pipecat 1.12.0 (`video_in_enabled`, `video_out_enabled`, `write_video_frame`); the `livekit` extra installs on Linux/CPython 3.12 and mints room tokens (28 MB native `liblivekit_ffi.so`); `livekit-client` 2.22.4 is on npm; the free Build tier covers demo use. The avatar stays out of scope but is now reachable — Pipecat 1.12.0 already carries a HeyGen transport that joins a LiveKit room.
* **Implemented so far** (T23–T26): the `vision` role with image parts through the openai wire as a `data:` URI and `redact()` keeping payloads out of logs; `ports/blobstore.py` with `local` and `gcs` adapters, server-side frame bounds, the self-re-enqueueing `prune_media` job and `GET /api/media/{id}`; the ninth module `evidence` (three tables, `ports/framesource.py`, the `look_at_camera` built-in, observations, pinned evidence, cases and routing, `visual_evidence` on the hand-off packet); and the LiveKit channel (`ports/videoroom.py`, room naming and token minting, `build_room()` beside `build()` sharing one set of processors, the frame tap, the 60-second no-participant timeout, degradation to voice). 74 new tests. Changed while implementing: `prune_media` is queued **per tenant**, because job rows carry a tenant and a service-wide job had no honest one to belong to; `visual.case_kind` was added to the agent config, falling back to the agent's mode so no agent has to declare it; `look_at_camera` joined the reserved built-in names.
* **Known weakest point**: the media path cannot be verified in CI. Both pipelines are constructed with dummy credentials and asserted to make no network call (as VO-06 already did for the WebSocket), but a real room needs credentials and a browser, so the live halves of VI-01 and VI-14 and all of UI-38…45 are hand-checked via `scripts/acceptance-baseline.txt`.

* **Decided while drafting, and the three things a reviewer should attack**: (1) **transport** — camera stills captured on demand over the existing call WebSocket, not LiveKit. LiveKit Cloud works and would also unlock an avatar, but the feature needs a handful of stills in one direction and the price is a hosted media service plus a second transport inside the module with the most volatile dependency ([ADR-0009](decisions/adr-0009-video-channel.md)). (2) **on-demand capture, not a frame buffer** — the first draft had the browser pushing a frame per second into a latest-frame buffer; on demand is better on consent (nothing leaves the browser unless the agent asked and said so), on freshness and on there being no buffer to bound, for the price of one round trip and a 2 s timeout (VI-15). (3) **a fifth agent for ward faults, not a skill on the Internal Knowledge Assistant** — a fault report involves no member and no verification and it *writes* rather than answers, and bolting it on would blur the one agent whose knowledge-isolation guarantee (UC-03) is load-bearing; the new agent has no document set at all (UC-07).
* **LiveKit Cloud checked properly after review, not assumed**: the transport ships in the pinned Pipecat 1.12.0 with `video_in_enabled`/`video_out_enabled`, the `livekit` extra installs on Linux/CPython 3.12 and mints room tokens (28 MB native `liblivekit_ffi.so`), and **LiveKit Cloud supplies managed TURN over TLS 443** - so ADR-0002's "WebRTC needs UDP, which Cloud Run does not support without a TURN server" is a weaker objection than it reads, and [ADR-0009](decisions/adr-0009-video-channel.md) no longer leans on it. What decided it instead is a measured gap: Pipecat 1.12.0 is the current release and its LiveKit transport pushes *every* inbound frame into the pipeline, with request-only delivery (`video_in_sources`, `on_request_only`) only in unreleased upstream work. Choosing LiveKit today would mean streaming a ward continuously to a third-party SFU to use two frames of it, which contradicts compliance rules 9 and 12 and VI-03. Recorded with a revisit condition, and with the avatar's path named: LiveKit plus the HeyGen transport that 1.12.0 already carries.
* **Named while drafting**: `FrameSource` has to be a port, not an import. The turn loop calls `evidence` through its contract and `voice` already names `conversation`, so `evidence → voice` would close the graph into a cycle and MOD-01 would fail — correctly. It is the clearest instance yet of the asymmetry [modular structure](architecture/modular-structure.md) describes.
* **Scoped out, with reasons rather than silence**: the talking avatar from the original idea (sending a video track *down* is the single requirement that forces a media server, so it is its own CP and nothing here blocks it), runtime image generation (a product that can synthesise a picture of damage inside the flow that files claims is one prompt from manufacturing its own evidence — IMG-01), PHI incidentally captured in a frame, deletion on request, and an access audit trail. The last three are now written into the production gaps instead of being implied as handled.
* **Not implemented.** This is a spec-only change under rule 1 of [AGENTS.md](../AGENTS.md): no code, no tests, every touched spec `status: draft` and the CP `proposed`. Implementation waits for `cp_state: accepted`; the task list is T23…T28 and the first two (the `vision` role and the blob store) are independent of the rest.

* **Clarification** while writing the specs: post-call analysis is a **port** owned by `ports/`, not a function on `learning`'s contract, because `learning` already names `conversation` to drive simulated calls and the module graph must stay acyclic — the asymmetry is the design. Escalation *triggers* cannot leave the turn loop, so `handoff` is drawn at the human console rather than at the safety screen. `analytics` owns no tables and exists so the dashboard has somewhere to read across modules from, which is the coupling it had.
* **Disproved while reviewing**: the readiness gate was *not* re-derived in the insights route as first thought; the real defect there is that three handlers build a 28-day, tenant-wide cluster aggregate to read one boolean. Also found, and not in the original review: `voiceai chat` drains the job queue without ever importing the handler modules, so its post-call analysis has silently never run.
* **Decided while implementing, and worth recording**: splitting the twenty tables into a `tables.py` per module was tried and **reverted**. Twenty-eight places read another module's tables and nearly all are SQL joins (the call explorer joins four tables across three modules; the dashboard three across three), so routing them through contracts turns one join into several round-trips - a real performance change dressed as a refactor, for a benefit that only lands when a module actually leaves the process. [Modular structure](architecture/modular-structure.md) now records table *ownership* and the three invariants that keep a later split cheap (reads only across boundaries, writes through contracts, no `relationship()` anywhere), rather than claiming a file layout that does not exist. The attempt also exposed a false positive in `arch_check`: MOD-07 matched the word `relationship()` in a docstring explaining the rule; it now matches the parse tree, with a regression test.
* **Also corrected**: the port table first listed a `SimulationRunner` for evaluation calls. It is unnecessary - fleet learning already depends on the conversation module, so a contract call is right and becomes the HTTP client if learning is extracted. Dropped, and the `HandoffDesk` port the work did need is named instead. Three cycles surfaced while moving code (conversation vs hand-off, agent configuration vs conversation, conversation vs voice); each is broken with a port, because the conversation module is upstream of everything that reacts to a call.
* Implemented: `scripts/arch_check.py` (seven static rules, run in CI; 17 tests on synthetic package trees), `ports/llm.py` and `adapters/llm/{registry,openai_compatible}.py` (the gateway keeps `stream_chat`/`chat`/`complete_json` and all its helpers, so no call site moved), `config.py` (`extra="allow"` plus `env_value()`, which also fixed an `and`/`or` precedence bug in `provider_configured`), `routes/meta.py` (`/healthz` derived from `models.yaml`), `config/models.yaml` (`wire:`, `options:`), `jobs.py` + `main.py` + `cli.py` (declared handler kinds, explicit registration, start-up error when one is missing), `db.py` (`get_owned`). 31 new tests (`tests/test_arch_check.py`, `tests/test_llm_wire_port.py`, `tests/test_tenant_scoping.py`); `tests/test_llm_gateway.py` retargeted to the wire adapter and its `real_mode` fixture isolated from the developer's own `apps/api/.env`, which had been making two role-fallback tests fail locally while passing in CI.
